# valorant-replay

前日（JST）に行われた VALORANT のプロ試合を、**翌朝 Notion のマップページを開くだけでふり返れる**ようにするパイプラインです。
重い処理は Google Colab の CPU（並列）と GPU（デコード）で動かし、コードはこのリポジトリから `git pull` して使います。

[![Open In Colab](https://colab.research.google.com/assets/colab-badge.svg)](https://colab.research.google.com/github/AK47bbddk/valorant-replay/blob/main/colab.ipynb)

## 何ができるか

```
vlr.gg 結果一覧 ──► 試合ページ（マップ・ラウンド勝敗・エコ・選手・マップ別VOD）
        │                              │
        │                              ▼
        │                  Notion「大会ログくん」「マップ詳細」に upsert
        ▼
YouTube の該当マップ区間だけ取得（yt-dlp、次のマップは裏で先にダウンロード）
        │
        ▼  キャリブレーション：放送レイアウト（Riot / CN）を自動選択、カード位置は ULT アイコンの丸から、
        │  キルフィードは選手名から自動検出
        ▼  並列スキャン（CPU 数ぶんのプロセス）：2fps でデコード、HUD を OCR（RapidOCR・見た目キャッシュ）
ライブ判定（スコアバーの見た目）でリプレイ・選手カメラ・解説席を除外 → ラウンド分割（スコア＋タイマー）
        │
        ▼  ラウンドごとに（スレッドで並列）
開始時ミニマップ ／ ミニマップ GIF ／ 購入パネル・各選手の武器 ／ キルログ（武器つき）／ ULT 使用 ／ YouTube リンク
        │
        ▼
Notion「マップ詳細」ページ本文 ＋ Drive に HTML レポート
```

各マップページの中身：

- 概要（VOD・VLR へのリンク、スコア、解析の信頼度と所要時間）
- **ラウンド一覧表**（1 ラウンド 1 行）

  | R | スコア | 勝者 | 勝ち方 | 勝因 | VIT 購入・武器 | LOUD 購入・武器 | 先制キル | キル | ULT 使用 | 時間 |
  |---|---|---|---|---|---|---|---|---|---|---|
  | R6 ▶ | 1-5 | LOUD | 💀全滅（攻撃） | 🔁リテイク・先制されて逆転 | フル 21.3k<br>ファントム×3・ヴァンダル・オペレーター | ハーフ 11.6k<br>ヴァンダル×2・シェリフ×2 | Derke→tkzin（VIT） | 3-5 | Darker（Waylay） | 1:05 |

- ラウンドごと（折りたたまず、スクロールするだけで 1 ラウンドずつ全部見える）
  - 見出し：R6　LOUD 勝利　1-5　勝ち方　▶（YouTube の該当秒）
  - **勝因**の囲み：主な勝因と根拠（例「リテイク：設置後に全滅（設置後 3 キル）」「1ピック：Derke→tkzin（0:12 経過）」）、設置時刻、ラウンド時間
  - **開始時のミニマップとラウンド中のミニマップ GIF を横並び**（GIF は 4 倍速・リプレイ除外）
  - 両チームの購入段階・残り資金・各選手の武器（メイン＋サブ）
  - キルログ（時刻・キラー［武器］→ 被キル、チームの色つき）、ULT（開始時に溜まっていた選手・使用）
  - 購入時の装備表とキルフィードの切り抜きを横並び

### 勝因の判定

キルの順番（キルログ）・スパイクの設置（タイマー欄が赤いアイコン／赤い秒数になった時刻）・VLR の勝ち方と攻守・購入段階から、
当てはまるものを重要な順に並べます（`vreplay/reasons.py`）。

| 勝因 | 判定のしかた |
|---|---|
| エース | 勝ったチームの 1 人が 5 キル |
| クラッチ | 勝ったチームが最後の 1 人になった時点で相手が 2 人以上 |
| リテイク | 守備側の勝利で、設置のあとに解除または全滅 |
| ポストプラント成功 | 攻撃側の勝利で、設置のあとに爆破または全滅 |
| ラッシュ | 攻撃側の勝利で、開始 30 秒以内に設置、または開始 20 秒で 2 キル以上 |
| カウンター | 守備側の勝利で、開始 20 秒以内に守備側が最初のキル、設置させずに勝つ |
| 数的不利から逆転 | 途中で 2 人以上少なくなってから勝つ |
| エコ勝ち／アンチエコ | 購入段階が下の側の勝利／上の側が落とさなかった |
| 初動Aファイト勝ち／初動Aファイト負けから逆転 | 最初のキルの直前に両チームの点がいちばん近づいた場所（ミニマップが合っているとき）。場所が分からなければ 1ピック／先制されて逆転 |
| Aエントリー成功 | 攻撃側が先制した場所に、そのまま設置して勝つ |
| オペレーターで1ピック | 最初のキル（または 2 キル以上）がオペレーター |
| トレード勝ち | 味方が倒された 4 秒以内に倒した相手を倒し返す、が 2 回以上 |
| マルチキル | 勝ったチームの 1 人が 3〜4 キル |
| ULTリテイク／ULTで攻め切り | 守備側が設置後に ULT を使って取り返す／攻撃側が ULT を使って勝つ |
| フォースバイ勝ち | ハーフ・フォースバイの側がフル装備に勝つ |
| 時間切れまで守り切り・設置前に全滅・設置させずに守り勝ち・ピストル | VLR の勝ち方と攻守・ラウンド番号から |

キルログが一部しか読めていないラウンドは、人数の流れが推定であることを囲みの中に書きます。

### 初動の配置のタグ

各ラウンドの開始 6〜20 秒にミニマップで見えた位置から、チームごとに初動の配置に名前をつけます
（守り：「A スタック」「MID 3」「MID 2」「バランス」「サイト守り（MID なし）」、攻め：「MID 3 デフォルト」「A 寄せ」
「A 寄りデフォルト」「A/Mid 分割」「散開デフォルト」）。人数の形（A2 Mid1 B2）とコールアウトの一覧も残し、
Notion・HTML の勝因の囲みに「初動：…」として出します。プレイブックでは、同じ名前でコールアウトの重なりが半分以上の
ラウンドを 1 つの型にまとめ、回数・勝率・初動のファイトの場所・設置サイト・例のラウンドを並べます。

### キルの拾い方

1. キルフィード：白い名前の行が 1 つでも映っているフレームは保存し、行ごとに見た目を覚えて、初めて見た行だけをその高さだけ
   切り出して OCR（読み違い対策に 1 秒後にもう 1 回）。画面全体を何度も読むより速く、行が下にずれても読み直しません。
   1 行を「いちばん広いすき間（武器アイコン）」で左右に分け、チームタグと名前が別の塊でも取り違えないようにします。
   同じチーム同士になった行は相手チームで読み直し、片側しか読めない行はもう片側を相手チームの名前から選びます。
2. カード：読めなかった人は、カードが灰色になった時刻で補います（ラウンド終了直前の 1 フレームでも採用）。
3. 全滅（elim）のラウンドは負けた 5 人全員が倒れているので、どこにも出なかった人を最後に生きていた時刻で補います。

ログの「キル キルフィード N・カードで補完 M・全滅から補完 K」で内訳が分かります。

### ULT の誤検出対策

ピストルラウンド（1・13）の開始直後に「溜まっている」と読めるカード、試合を通して 8 割以上「溜まっている」カードは
枠がずれているとみなし、そのカードの ULT は出しません（ログに「ULT の読み取りが当てにならないカード L1」）。
カードの位置は ULT アイコンの丸から等間隔に当てはめますが、1 段ずれると「左1」のように名前が読めなくなるので、
上下に 1 段ずらした位置で選手名を読み、VLR の選手名にいちばん多く合う位置を選びます。

## 大量の過去試合をまとめて分析する

2024〜2026 の VCT Tier1 をまとめて見たいときは、**メタデータ → 動画 → プレイブック**の 3 段階で回します。

```powershell
# 1) 試合・マップ・ラウンド・選手・VOD 秒を SQLite に入れる（動画は取らない）
vreplay backfill --from 2024-01-01 --to 2026-12-31

# 2) 未処理マップを動画解析する。止めても再実行で続きから
vreplay batch --limit 20

# 3) チーム×マップ、構成×マップの HTML を作る
vreplay playbook
```

- DB は既定で `<output.dir>/warehouse.sqlite3`。`warehouse.path` で変更できます。
- `backfill` は VLR の結果一覧を新しい順にたどり、試合ページを 1 件ずつ読みます。数千試合だと数時間かかるので、`--limit` で区切って実行してください。`--dry-run` で候補数だけ確認できます。
- `batch` は `status='done'` のマップを飛ばします。`--no-retry` で失敗済みも飛ばします。`--shard 1/4` のように分けると、別プロセス・別出力で並列に回せます（同じ DB に同時書き込みしないでください）。
- `playbook` は `output.dir/playbook/index.html` に出ます。`--min-maps 3` で少ないサンプルのチーム・構成を省けます。チーム別ページにはサイト集計に加えて、初期配置・ローテーション・リテイク・デフォルト・中盤・最終セット・ポストプラント・1ピックの型を出します。
- 動画解析の出力は従来どおり日付フォルダに `report.json` と画像が残ります。`batch` は最後に日付ごとの HTML も作ります。

### プレイブック（Notion）

`vreplay playbook --notion <親ページの URL>`（Colab のプレイブックのセルの `NOTION_PARENT`）で、チーム × マップ × 構成ごとに
Notion にも書きます（親ページをインテグレーションに共有しておいてください）。形はチーム内でよく使うプレイブックにそろえています。

- `# 概要` → `## ATK summary`（方針の箇条書き）→ **ATK のデータベース** → `## DEF summary` → **DEF のデータベース** → `## メモ`
- データベースの 1 行 = 1 つの型。名前は人数の形＋型の名前（「1-3-1 MID 3 default」「A Site Rush」「B retake」）、
  種類（Default / Set / Retake）・回数・勝率・購入・タグ（形・解説の言及）つき
- 各行のページは左に説明（回数・勝率・よく映る場所・その後の設置・初動ファイト・解説の言及）と例のラウンドの動画（該当秒から再生）、
  右にその型のときの位置をマップ画像に重ねたもの
- シークレットに `OPENROUTER_API_KEY`（DeepSeek V4 Flash の無料版）か `GEMINI_API_KEY`（Gemini の無料枠）があれば、ATK / DEF summary の文章を LLM が集計から書きます（`--no-llm` で止める）。どちらも無料で取れ、クレジットカードは要りません。
  渡すのは数字・型の名前・解説の一節だけで、データにないことは「推測：」と分けて書かせます

### 意図の読み取り（解説の字幕）

放送の自動字幕を yt-dlp で取り（動画の数百分の 1 の大きさ）、各ラウンドの購入フェーズ〜終了の字幕から
ラッシュ・スプリット・フェイク・ラーク・リテイク・ローテ・スタック・デフォルト・ミッドコントロール・エコ/セーブ・フォース・
オペレーター・ポストプラント・遅延・エントリー・クラッチ・ULT・タイムアウトの言及と、根拠の一節（100 文字以内）を拾います
（`vreplay/captions.py`）。Notion・HTML の各ラウンドに「解説：…」、プレイブックに「解説から読み取れる意図」として出します。
相手チームの話のこともあるので、数字とは分けて「言及」として扱います。

### プレイブック（スライド）

`vreplay playbook` は、ためた解析結果から **チーム × マップ × 構成** ごと（と、2 マップ以上ある **構成 × マップ** ごと）に、
「Split G2 Comp PlayBook」のようなスライドを `output.dir/playbook/` に作ります（Colab のプレイブックのセルで表示・ダウンロード）。
画像は HTML に埋め込んであるので 1 ファイルで開け、印刷すると 1 スライド 1 ページの PDF になります。

| スライド | 中身 |
|---|---|
| 表紙 | マップ・チーム・構成、元にした試合 |
| Defender / Attacker Strategy | **strong point ①②③ / weak point ①②**。同じマップの全チーム平均と比べて差が大きい指標から自動で選び、根拠の回数・平均・関わった選手・例のラウンド（YouTube の該当秒）を添える |
| Concept | 1:30・1:15・1:00・0:40 のゾーン別の平均人数と、そこから読める方針（例：「MID は 1:30 に 2.0 人 → 0:40 は 0.4 人。時間を見て MID を減らしサイトでセットを受ける」）、位置の重ね合わせ画像 |
| Default 一覧 | 1:15 の配置の型（MID 3／A スタック／バランス…）× Buy/Eco ごとの回数・勝率・例 |
| Sets（攻め） | 設置サイト × 攻め方（Rush＝0:30 以内／Split＝MID とサイトの両方から／Site Set／Late Set＝1:00 以降） |
| How to Retake A/B（守り） | 設置されたラウンドのリテイク成功率、設置時点の自チームの位置、リテイクで使った ULT、例 |
| A/B Site PostPlant（攻め） | 設置後の勝率、設置直後の位置、設置後の ULT、例 |
| ULT・選手と経済・データ | エージェント別の ULT の使用回数・勝率・使う時刻、選手のキル・先制・先に落ちる回数、ピストル・エコ・アンチエコ |

strong / weak point で使う指標：ラウンド勝率、購入ラウンドの勝率、先制キル率、先制後／先制された後の勝率、
開始 20 秒以内の先制（カウンター）、設置させずに勝つ率、リテイク成功率（サイト別）、設置率、ポストプラント（サイト別）、
ラッシュ・遅めのセットの勝率、時間切れ負け、終盤（0:40 以降）の勝率、ULT を使ったラウンドの勝率、ピストル・エコ・アンチエコ。
回数が少ないと極端な値が出るので、平均へ 3 ラウンドぶん寄せた値で比べ、差が 7 ポイント以上のものだけを出します。
「なぜそうするか」（スキルの使い方・コール）は動画からは分からないので、人の解説を足して完成させる叩き台です。

データは毎日の `run` で自動的にウェアハウス（SQLite）にたまります（設置時刻・設置サイト・勝因・節目ごとの配置・
キルの出どころも保存）。以前の実行分は `vreplay playbook --sync`（または `vreplay sync`）で 1 回取り込んでください。
以前の集計ページ（ヒートマップ・型の表）は `playbook/stats/` に出ます。

### サイト・位置の見方

`tactics.py` は放送ミニマップのチーム色の点を検出し、valorant-api.com のコールアウト（A/B/C、Mid、スポーン）に近い順で分類します。座標はミニマップ画像の 0〜1 に正規化し、16×16 のヒートマップにしています。

- まず**地形**で合わせます：ミニマップの背景（何枚かの中央値）から明るい床を取り出し、コールアウトが床の上に乗り、
  床全体に広がる回転・倍率・位置・鏡映を探します。サイトの黄みがかった四角（A/B/C の文字）が見つかれば、サイトの
  コールアウトがその近くに来る候補を優先します。床から離れた点（UI のちらつき）は位置の集計から捨てます。
  実際の放送（Champions 2026 の Split・Haven。どちらも 90 度回して表示）で、コールアウトが正しい場所に乗ることを確かめています。
- 床は半透明で、後ろの試合画面によって色が変わります。明るさの二値化と、白い縁の線のすぐ内側の色から推定した床の色の
  2 通りで床を作り、縁が白い線と重なる方を使います。向きは 90 度単位 ±12 度、倍率は切り抜きいっぱい前後、鏡映なしに絞ります。
- サイトの四角の文字（A/B/C）を OCR で読み、読めた四角にはそのサイトだけを対応させます（Sunset のように左右がほぼ対称のマップで
  A と B を取り違えないため。2 サイトのマップは片方が読めればもう片方も決まる）。
- 「暖色がチーム1か」は、カードから分かるチームごとの生存人数とミニマップの色ごとの点の数が合う方で決めます（人数に差がある時刻だけ）。
- 地形で合わせられないときは、試合中の点から**回転・倍率・位置**を推定して
  コールアウトを重ねます（`vreplay/minimap.py`）。各ラウンドの開始直前に攻撃側 5 人がスポーンに固まることを錨にし、
  試合中に点が通った場所とコールアウトの両方向の距離が最小になる変換を選びます。「暖色がチーム1か」も同時に決めます。
  ログの「ミニマップ合わせ：回転 …・倍率 …（一致 …・2 位との差 …）→ 信頼度 …」と、HTML レポートの
  「ミニマップ合わせの確認」の画像（コールアウトが地形の上に乗っていれば OK）で確かめられます。
  合わせられないときは以前の方法（90 度単位の向き）で目安だけ出し、プレイブックの位置のスライドには使いません。
- 設置サイトは、スパイク設置直後 10 秒の攻撃側の位置で決めます。
- それでもサイト名は近似です。各ページに `confidence` と `site_conf` を出しているので、低いときは話を広げすぎないでください。
- ミニマップが試合中に切り替わる放送や、チーム色が暖色/寒色以外の場合は検出が外れます。`config` の `tactics.*` でサンプリング間隔や点の面積を調整できます。

### ラウンドの型（プレイブック）

`patterns.py` は `tactics.py` が保存したチーム単位のミニマップ点を、次の時間帯に分けて型を推定します。

- 初期: ラウンド開始 5〜18 秒。防衛の初期配置、攻撃のデフォルトを見る。
- 中盤: 18〜50 秒。ローテーション、圧力の移動、1ピック後の再構成を見る。
- 終盤/設置後: 終盤 35 秒とプラント後の位置。最終セット、ポストプラント、リテイクを見る。

人数は「1 サンプルあたりの平均人数」で、`A2 B2 Mid1` のように表示します。選手 ID までは取れないため、個人のルートではなくチームの重心・人数分布として扱います。1ピックはキルフィードの先頭キル時刻と、その前後のチーム位置から推定します。

再解析前の DB には `positions` がないため、型の表は「データなし」になります。`batch` で再解析するか、対象マップを `run` し直すと追加されます。

### 解析時間を短くする

`scan` は HUD スキャン時にミニマップを `frames_*` に保存しています。`tactics` はその保存済み画像を再利用するため、以前のように動画をもう一度デコードしません。同じマップを再解析するときも、スキャン結果とフレームが残っていれば `tactics` の負荷は下がります。

### 現実的な規模

全期間の動画を 1 台で解析すると、ダウンロードだけで数 TB・解析に数週間かかります。まず `backfill` で全試合のメタデータを入れ、`playbook` で大会・チーム・構成の傾向を見てから、見たいチーム/マップに `batch --from ... --to ...` を絞るのがおすすめです。`video.download_workers` と `video.download_fragments` を上げると速くなりますが、回線と YouTube のボット判定に注意してください。

### 方法 A：自分の YouTube の cookies を渡す（手軽・Colab だけで完結）

1. ブラウザで**シークレットウィンドウ**を開き、YouTube にログインする（BAN のリスクを避けるならサブアカウント推奨）。

3. 拡張機能「Get cookies.txt LOCALLY」などで youtube.com の cookies を **Netscape 形式**で書き出す。
4. シークレットウィンドウを閉じる（開いたままだと cookies が更新されて無効になる）。
5. 書き出したファイルを Drive の `MyDrive/valorant-replay/cookies.txt` に置く。
   （または中身を Colab の 🔑 に `YT_COOKIES` として登録）

cookies は数週間〜数か月で切れます。またボット判定が出たら書き出し直してください。

## 精度について

実際の放送（VCT China 2026 Threshold と Champions 2026 Shanghai）から切り出した HUD で確かめています（`tests/`）。

- **リプレイ・非ライブの除外**：画面上部のスコアバーの見た目を、タイマーとスコアが読めたフレームから作ったお手本と比べます。
  リプレイは別のミニバー、選手カメラや解説席はバーが無いので外れます（実データで、ライブとの差 2〜4 に対しリプレイは 24 以上）。
- **ラウンド分割**：ライブのフレームのスコア合計＋1 をラウンド番号とし、確定した増加だけを採用します。
  開始は購入フェーズ（0:30→0:00）のあと 1:40 付近に跳んだ瞬間で、映っていなければ残り時間から逆算します（実データで誤差 1 秒以内）。
  タイマーが止まった区間（テクニカルポーズ）はライブ区間から除きます。
- **武器**：ラウンド間（購入フェーズ〜開始直後）に出る**装備表**から読みます。表の位置は選手名を OCR で見つけて決め、
  名前と同じ行にある白いシルエットを 1 つずつ切り分けて、メイン武器とサブ武器を判別します
  （valorant-api.com の武器アイコンと実際の放送から切り出した見本に重ねる。見本は `vreplay/data/` に同梱）。
  VCT CN の実際の装備表 30 人ぶんで、ゴースト・クラシック・シェリフ・ショーティー・スペクター・ガーディアン・
  アウトロー・ファントム・ヴァンダル・オペレーターを全員正しく判別（`tests/test_loadout.py`。オペレーターとアウトローは
  この表から切り出した見本も足しています）。
  - **リプレイが開始直前まで流れていても大丈夫**：開始 9 秒前〜3.5 秒後の 2fps の画面を開始に近い順に見て、
    表が映っているフレーム（見た目の下見＋名前が 6 人以上読める）だけを使います。最後の 3 枚の多数決。
  - 表が 1 枚も映っていないラウンドは、開始直後の試合中カード（タイマーとスコアが読める＝リプレイでない画面）から読みます。
    このときはラウンドの注記に「試合中のカードから読みました」と出ます。
  - 自信がないときは「不明」と表示します。
- **抜けたラウンドの補い**：スコアの読み違いで 2 つのラウンドが同じ番号になったときは、タイマーが購入フェーズから
  1:40 付近へ跳ぶ位置（各ラウンドに 1 回）で区切り直します。ページ冒頭の灰色の行に「タイマーから補ったラウンド」
  「見つからないラウンド」を出します。
- **ULT**：アイコン外周の点線が全部つながって光ると「溜まっている」。生存したまま光った輪が消えたら「使用」です。
  使用直後に倒されて空のフレームが 1 枚しか無い場合も拾います。倒されたカードは灰色になるので判定から外します。
  誰が使ったかは、ラウンド開始直後の試合中UIから読んだ名前・エージェント・チームで表示します。
- **選手名**：カードの名前欄を複数フレームで読み、VLR の出場選手に多数決で寄せます（実データで 20 人中 20 人一致）。
- **CN 放送の UI**：購入前とラウンド中でカード位置が変わるため、タイマーで2群に分けて別々に検出します。
  ラウンド開始は購入タイマーと1:40カウントダウンの両方から推定し、信頼度をレポートに残します。
- 解析が一部失敗しても、VLR 由来のデータとスクリーンショットだけでページは作られます。ページ冒頭の灰色の行に読み取り率が出ます。

## 速さについて

**動画の取得**：YouTube は 1 本の接続を 1 MB/s 前後に絞るので、本数で稼ぎます。既定は区間を 16 に分けて yt-dlp で同時に取る方法です
（Colab で 12〜16 MB/s。次のマップの取得は解析と並行して進むので、待つのは最初のマップだけ）。
Colab では範囲取得（下）に使える形式が返らないことが多かったので、`video.download_method: range` は試したいときだけにしています。
まず DASH の目次（sidx）から必要な時間帯のバイト範囲だけを 16 本同時に取ります（`video.download_method: range`）。
URL の取得と通信はプロセス内の yt-dlp（区間取得と同じ cookies・クライアント・JS ランタイム）で行い、
クライアント（tv・web_safari・既定・visionos・mweb・android_vr）ごとに、DASH（mp4）なら 1KB だけ取ってみて Range ヘッダーか
`&range=` で通るものを、DASH が無い・拒否されるクライアントでは HLS（m3u8）のプレイリストから必要な時間帯の断片だけを
並列に取ります（既定クライアントの DASH は PO トークンが無いと 403 になり、tv などは HLS だけを返すため）。どれも通らなければ区間を 16 分割して yt-dlp で同時に取ります（2 回続けて失敗した実行では範囲取得を試しません）。
ログに「必要な範囲だけを 16 本同時に取得しました（取得方法 tv・Range ヘッダー）」か、失敗した理由がクライアントごとに出ます。

動画の解析は 2 段階です（`video.scan_mode`、既定 `auto`）。

1. **キーフレームだけを読む**：動画は数秒ごとの「キーフレーム」だけなら、ほかのフレームをデコードせずに取り出せます。
   全フレームをデコードするより 10 倍以上速く（手元の計測で 60 秒の 1080p60 が 9.5 秒 → 0.6 秒）、
   これでタイマー・スコア・ライブ判定・ラウンドの位置をつかみます。
2. **必要なところだけ 2fps で読む**：
   - `fast`（キーフレームが 2.5 秒以内おきの動画。YouTube はふつうこちら）… 装備表が出る「開始 9 秒前〜3.5 秒後」だけ。
     ミニマップ GIF・キルログ・ULT はキーフレームの画像を使います（GIF は実際の間隔どおりの 4 倍速）。
   - `rounds`（キーフレームが 6 秒以内おき。VCT CN の配信は約 4.8 秒おきでこちら）… 各ラウンドの「開始 9 秒前〜終了」を 2fps。
     終了は「残り時間が開始からの経過と合う最後のフレーム」から決めるので、ラウンド後のリプレイや購入フェーズは読まない。
   - `full` … 全区間を 2fps（以前の方式）。

ほかに：

- **動画の取得**：YouTube は 1 本の接続を 1 MB/s 前後に絞る（2 GB のマップで 30 分以上）ので、マップの区間を
  8 つに分けて同時に取得します（`video.download_parts`）。分けたファイルは `*.parts.json` でつなぎ、解析側は 1 本の動画として読みます。
  マップは 1 つずつ全力で取り、解析している間に次のマップを取ります（`video.download_workers: 1`）。
- **GPU**：T4 などの GPU があると、デコード（NVDEC）に加えて OCR も GPU で動かします（セル1で onnxruntime-gpu を入れる）。
  デコードしたフレームは GPU の上で 2fps に間引いてから CPU に移すので、60fps の全フレームを CPU にコピーしません。
  ログの「スキャン」の行に「デコード GPU・OCR … 回 GPU」と出ます。
- **Notion への書き込み**は裏で進め、次のマップの解析と同時に行います。画像は 4 本同時に送ります（リクエストの開始は 3 回/秒まで）。
- **キルログ**：キルフィードの背景は半透明でゲーム画面が透けるため、画像の差分だと毎フレーム「変化あり」になり、
  OCR が何百回も走っていました。白い名前の行に「新しい行」が出たフレームだけ OCR するようにしています。
- 解析は CPU 数ぶんのプロセスで同時に行い、OCR のスレッド数を「CPU 数 ÷ プロセス数」に合わせて取り合いを防ぎます。
  OCR のモデルはプロセスごとに 1 回だけ読みます。
- HUD の数字は同じ見た目が何度も出るので、見た目が一致したら前の結果を使い回し、実際の OCR は 1 割程度に減らしています。
- 装備表は、見た目の下見で「表が出ていない画面」を OCR の前に捨て、表が出ているフレームだけ武器を読みます。
- ミニマップ・選手パネルの切り抜き保存は既定で 1 秒間隔です（`video.minimap_every` / `video.panel_every`）。
- キルフィードは見た目が変わったフレームだけ保存します（`video.killfeed_on_change`）。
- GPU は動画のデコード（NVDEC）に使います（ffmpeg が対応していれば自動。ログに「デコード GPU」と出ます）。
- 解析中に次のマップの動画を裏でダウンロードします（`video.download_workers`、既定 2 本）。
- 1 本の動画は yt-dlp が分割して並列取得します（`video.download_fragments`、既定 4。回線が速いなら 8 などに）。

ログの「スキャン」の行に、どのモードで何分ぶんを密に読んだかが出ます。

```
スキャン 1490 枚 1 分 10 秒（高速モード：キーフレーム 1250 枚（間隔 2.0 秒）＋密に 5.0/42.0 分・8 並列・デコード GPU・OCR 900 回）
```

### 処理時間とリソースの表示

各処理のあとに、**所要時間とそのときの Colab の CPU・GPU・RAM** をログに出します。

```
動画を取得：Summit（780 MB, 1 分 12 秒, 10.8 MB/s）｜CPU 平均 8%（最大 34%）｜GPU なし｜RAM 最大 3.1/12.7GB
スキャン 532 枚 2 分 05 秒（8 並列・デコード GPU・OCR 420 回）｜CPU 平均 91%（最大 100%）｜GPU 平均 18%（最大 47%）・VRAM 最大 1.2GB｜RAM 最大 5.8/12.7GB
```

最後に全体の集計と、余っているリソースに応じたヒント（ダウンロードが長い／CPU が余っている など）を出します。

- 日付フォルダの `perf.json` に生データ（1 秒ごとのサンプルと処理ごとの集計）を保存
- HTML レポートの先頭と各マップの「処理時間とリソース」に同じ内容を表示
- Notion のマップページにも 1 行で「処理時間：動画の取得 32 秒／キャリブレーション 8 秒／…（CPU 最大 96%・GPU 最大 21%・RAM 最大 5.8GB）」を表示

GPU 使用率は `nvidia-smi`、CPU・RAM は `psutil` から読むので、GPU の無い環境でも動きます（その場合は「GPU なし」と表示）。
