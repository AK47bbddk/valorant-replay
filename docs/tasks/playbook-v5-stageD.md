# 指示書: プレイブックv5 段階D v2（視点修正＋攻め分類＋暫定バリアフィルタ）

宛先: 実装エージェント（agy / Gemini 4 Hydrogen）
窓口: Muse / 承認: 青木（2026-11-14）
経緯: v1 の質問事項への回答を反映した改訂版。前回の停止は正しい判断だった。今回の定義はすべて決定済みとして進めてよい。

## 対象は3件

### D0: 分類の視点を直す（最優先・混線の根本修正）
現状の欠陥: phases.classify_flow は全ラウンドを攻撃側視点で型付けしている（序盤の型は攻撃チームのゾーン分布から作る）。段階Cはラウンドをサイド別に分けたが型の視点が攻めのままなので、防衛ブロックの型が「相手の攻め方」になっている。

修正: 型付けを「その構成のチーム視点」にする。
- 攻撃ラウンド: その構成の攻撃の振る舞いで型を付ける（D1の体系）
- 防衛ラウンド: その構成の防衛の振る舞いで型を付ける
  - 序盤 = 防衛の配置の型（防衛チームのゾーン分布から。主ゾーンで A／MID／B の寄せを表す）
  - 中盤 = 防衛の強い動き（ローテート、寄せ、上がり。イベントの side 属性を使い防衛側のイベントで判定する）
  - 終盤 = 寄せ方／リテイクの仕方（既存 _defense_late_kind を活かす）
- 型の説明文も視点に合わせる（防衛ブロックで相手の攻めを主語にしない）

### D1: 攻め側の分類（型体系と定義は決定済み）
攻めブロックは「開幕の型／エントリー／ポストプラント」の3部とし、中盤セクションは攻めでは出さない。

開幕の型（5種に正規化する）:
- Aデフォルト / MIDデフォルト / Bデフォルト: 既存 _early_type のゾーン分布の仕組みを使い、表記をこの形に統一する
- ラッシュ: 既存定義（開幕15秒以内のエントリー、最優先）。型は「ラッシュ」の1種とし、対象サイトは属性として併記してよい
- 詰め待ち: 既存の「分布なし」の場合に相当。約10秒動かない型として扱う

エントリーの型（サイト別、実在する型だけ出す）:
- 定義: サイトへのエントリー時点のウィンドウで、進入した攻撃側メンバーが直前にいた進入路エリアの種類数を数える。1種 = セット、2種以上 = スプリット
- 語彙: Aセット / Bセット / Aスプリット / Bスプリット。3サイトマップでは各サイトに用意する（Cセット / Cスプリット等）

ポストプラント:
- プラント後5秒以降の最初のサンプルで、生存している攻撃側の配置をクラスタリングする（PATTERN_DIST=0.09 を流用）
- サイト別に上位2種まで紹介する。2種に満たなければある分だけ
- 型名は配置のコールアウト構成から付ける（既存の説明文の作法に合わせる）

### D2: 開幕の誤検出への暫定フィルタ（青木の決定: 暫定で先行）
前提の訂正: バリア線の幾何データ（walls/spawns）は Sunset の設定にのみあり、Split にはない。今回は幾何を使わない暫定フィルタで進める。

ルール:
- 対象は各エージェントの最初期サンプル（最初のサンプル＋開幕ウィンドウ内）
- 最初のサンプルが、所属サイドの自陣側コールアウト集合の外（例: 攻撃側なのに開幕時点でサイト内や敵陣側、Mid Top 等）にある場合は誤検出として落とし、次の有効サンプルを開幕位置とする。自陣側の集合はマップのコールアウトデータからサイド別に定義する。定義のないマップではフィルタは無効（何もしない）
- あわせて連続性チェック: 開幕ウィンドウ内で、5秒間隔ではあり得ない距離のジャンプがあるサンプルは外れ値として落とす
- フィルタは tracks の正規化入口（_norm_tracks 等）に置き、分類と配置抽出の両方に効かせる
- 落とした件数を数え、生成物（manifest 等）に残して窓口が実データで確認できるようにする

## 検証への追加
- 防衛ブロックの序盤の型が、防衛側の語彙・視点で作られていること（合成データのユニットテストで、防衛ラウンドの型が防衛チームの分布から決まることを確認）
- 攻めブロックに中盤セクションが無いこと、開幕の型が5種の語彙であること、エントリー型がサイト別セット／スプリットであること、ポストプラントがサイト別2種以内であること
- バリアフィルタ: 最初のサンプルが自陣外にある合成ケースで落ちること、実データで落とした件数が報告されること
- 段階Cの検証（サイド整合・3部構成など）が引き続き通ること。防衛ブロックの構成（序盤／中盤／終盤）は段階Cの形を保つ
