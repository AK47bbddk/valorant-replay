※窓口 (Muse) が 2026-11-13 に作成。青木の決定（分類ルール叩き台への回答、2026-11-13）に基づく。ブランチは `task/playbook-v5-fixes` から `task/playbook-v5-phases` を切る。
※この指示書は段階A（分類の仕組みまで）。ページへの組み込みと図の差し替えは段階Bで別途指示する。

## 目的
ラウンドを「エリア支配のイベント列」として読み、序盤・中盤・終盤の区間と型を機械で付ける。プレイブック v5 の説明を、静止した配置の型から「アクション→リアクションの応酬の流れ」に作り替えるための土台。

## 材料
- `report.json` の `rounds[].tactics.tracks`: 全選手の5秒間隔サンプル `[経過秒, x, y, conf, src, zone, callout]`（位置→エリア変換は生成時に完了済み）。`kills` は時刻つき、`plant_t` あり。
- tracks を持たないラウンドは分類対象外とし、件数を数えて報告する（落とさない・混ぜない）。

## 定義（青木の決定を含む。数値はモジュール先頭の定数にする）
- ゾーン: A／Mid／B（3サイトマップは C も）。tracks の zone から取る。
- 支配: ゾーンに自チームが2人以上いて、相手より多い状態。
- 初期配置: ラウンド開始時点で入っているエリアは支配として数えない。イベントは支配の変化から拾う。
- テイク: 支配が無→自チームに変わる（次のサンプルまで続くこと）。
- 取り返し: 相手の支配だったゾーンを自チームの支配に変える。
- プッシュ（序盤・中盤の前進）: コールアウト単位で、相手側のエリアへ2人以上が進む動き。
- プッシュ（サイトエントリー後）: サイトより奥のエリアへ進んだ場合をプッシュとする。
- ローテート: チームの人数の重心ゾーンが変わり、次のサンプルも維持される。
- エントリー: 攻撃がサイトのコールアウト（A Site／B Site 等）に2人以上入る。
- ピック: キル（時刻つき）。
- フリーズ区間: ピックの後、支配の変化もキルも無いまま **10秒** 以上過ぎる。
- ラッシュ: 開幕から **15秒** 以内にサイトへエントリー、または人数の重心が一気にそのサイトへ寄る。

## 区間の切り方
- 序盤: ラウンド開始〜最初のピック、または最初の支配交代のどちらか早い方まで。
- 中盤: 序盤の終わり〜プラントまで（プラントが無いラウンドはラウンド終了まで）。
- 終盤: プラント後〜ラウンド終了。

## 型（イベント列のパターンとして判定する）
- 序盤: 詰め待ち／A・B・MID・C デフォルト／A・B・C ラッシュ。
- 中盤: フリーズ（ピック後にフリーズ区間）／リグループセット（散っていた人数が1ゾーンに集まり直してからセットでエントリー）／フェイクセット（片側で支配イベント→相手のローテート→反対側でエントリー）。
- 終盤: サイト耐え／プッシュ（サイトより奥へ）／下がる。
- 優先順位: フェイクセットとリグループセットが両方当てはまる場合は **リグループセット** を優先する。その他の重なりは、最初に成立した型を主とし、候補として併記する。
- 件数の下限は設けない（該当ラウンドが少なくても型として出してよい。青木の決定）。

## 成果物
1. 新規モジュール `vreplay/phases.py`:
   - `round_events(round_dict) -> list[Event]`（時刻・種別・ゾーン・側を持つイベント列）
   - `segment_phases(events, round_dict) -> dict`（序盤・中盤・終盤の区間）
   - `classify_flow(round_dict) -> dict`（区間ごとの型、イベント列、1行の流れ要約。例: 「防衛 A プッシュ→攻撃 Mid テイク→防衛 ローテート→攻撃 A エントリー」形式の文字列）
   - tracks が無いラウンドは `None` を返し、理由を区別できること。
2. 集計スクリプト `scripts/phases_report.py "<data glob>" --map Split --out <出力先>`:
   - 構成（マップ×5人）ごとに、型の件数と代表ラウンド（マッチ・ラウンド番号・流れ要約）を JSON と Markdown で出す。
   - 分類できたラウンド数／tracks 無しで対象外になった数を先頭に出す。
3. テスト `tests/test_phases.py`: 合成 tracks で各イベント（テイク・取り返し・ローテート・エントリー・フリーズ）と各型（ラッシュ15秒境界・フリーズ10秒境界・フェイク対リグループの優先順位・サイト奥プッシュ）を固定する。ネットワークなし。

## 追記（2026-11-13、段階Aの調整。窓口が実データ集計で確認した問題）
初版（7a11790）の実データ集計（Split 18レポート・分類184件）で次が判明した。定義は変えず、判定の当て方を直す。

1. 序盤がほぼ全部ラッシュになる（Fade構成で Aラッシュ70・Bラッシュ51・詰め待ち1、デフォルト0）。原因は「人数の重心が一気に寄る」の判定が、開幕の移動だけで発火していること。
   - ラッシュは「開幕15秒以内にエントリー（サイトのコールアウトに2人以上）」か「15秒以内に攻撃4人以上がそのサイト側のゾーンに入る」で判定する。重心（最頻ゾーン）の変化だけではラッシュにしない。
   - 序盤にエントリーせず、開幕配分がゾーン中心のラウンドはデフォルト（A／B／MID／C）に落ちるのが通常のはず。その形の合成テストを足して固定する（ゆっくりしたデフォルトのラウンドがラッシュにならないこと）。
2. 流れ要約がラウンド全体のイベント列のままで、区間ごとに切れていない。要約は区間（序盤・中盤・終盤）ごとに分け、`classify_flow` の戻りと集計レポートの代表欄は、その区間のイベントだけを見せる。
3. イベントが細かすぎる（ローテートとテイクが5秒ごとの揺れで量産される）。
   - ローテートは2サンプル続いた場合だけ発火し、10秒以内の逆戻りは取り消す。
   - 同じゾーン・同じ種別の連続イベントは1つにまとめる。
4. 集計レポートの先頭に、序盤・中盤・終盤それぞれの型の分布（全体件数）を出す。窓口が分布の偏りを判定に使う。
