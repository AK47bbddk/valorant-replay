# main-region-fix（Main 系エリアの色がサイト側＝プラント帯域へ届く問題の修正）

※この指示書は Muse（窓口）が 2026-11-10 に作成。青木の目視指摘（「BメインとAメインがサイト側まで来ているように感じる。プラントできる位置とサイトは近いが別の概念として考えて」）を受けたもの。

## 背景（確認済み 2026-11-10）
- 新 kb で生成した LOUD の Sunset プレイブック（Champions 2026、3マップ）で、A Main / B Main の色つき領域がサイト入口を越えてプラント帯域の近くまで届いて見える、とコーチが指摘した。
- 領域は `vreplay/mapfig.py` の `area_regions` が「通路画素 → 最寄りのコールアウト（重みつきボロノイ）」で決めている。境界は幾何学的な中点で決まるため、チョーク（概念上の境界）と一致しない。特に B Main はバイタルでないため重み（shrink）も無く、境界がサイト側に寄る。
- 実測（生成済み HTML の SVG 座標）: A Main 領域は x 最大 855（A Site ラベルは x=884）まで届く。B Main 領域は x 46〜545 の広範囲。
- 既存テスト（test_playbook_v4 の Sunset バイタル検査）は「A Main が A Elbow / A Site のコールアウト点を含まない」ことしか見ておらず、プラント帯域（Elbow と Site の点の間）への食い込みは検出できない。

## 概念の決定（青木、2026-11-10）
- **プラントできる位置（プラント帯域）とサイトは近いが別の概念**として扱う。Main 系エリアの範囲はチョークで止まり、プラント帯域に入らないこと。境界の判定は「Site のコールアウト点を含むか」ではなく「プラント帯域に届くか」で行う。

## やること
1. サイトごとのプラント帯域を表すアンカー点を kb 側に持てるようにする（例: `config/kb/maps/sunset.yaml` に `plants: {A: [x, y], B: [x, y]}` のような 0..1 座標。座標は公式マップ上のデフォルトプラント位置とし、根拠をコメントに書く）。名前・形式は既存の kb の流儀に合わせてよいが、テストから参照できる形にすること。
2. `area_regions` で、プラントのアンカー点をサイト側エリアの所有として領域計算に効かせる（= Main 系の領域がプラント帯域を越えなくなる）。既存の shrink（バイタルの重み）の仕組みと矛盾しない形にする。難しければ shrink の適用範囲を choke: true のエリアへ広げる案に切り替えてよいが、その場合は理由を報告に書くこと。
3. 回帰テストを追加する: Sunset で A Main / B Main の領域がプラントのアンカー点を含まないこと（test_playbook_v4 の既存検査と同じ実座標ベースで）。対象は実マップの下地を使う形が望ましいが、既存検査と同じ全面通路の下地でもよい（その場合は理由を書く）。
4. 既存テスト（test_kb / test_playbook_v4 / test_gamemodel / test_tactival / test_meta / test_deck）を全て通すこと。色なしエリアや他のマップ（Split 等）の領域が壊れていないこと。

## 触ってよいファイル
- `vreplay/mapfig.py`（area_regions とその周辺のみ）
- `vreplay/kb.py`（plants の読み込みが要る場合のみ）
- `config/kb/maps/sunset.yaml`（plants の追加のみ。エリア・手の変更はしない）
- `tests/test_playbook_v4.py`、`tests/test_mapfig.py`（回帰テストの追加）
- 触らないもの: 他マップの YAML、deck.py の表示まわり、PROMPT.md（規則の文言は窓口が別途やる）

## 完了の定義
- 上記テストが通り、Sunset のプレイブック再生成で A Main / B Main の領域がプラント帯域に入らないことを数値（アンカー点の含有検査）で示せること。レビューパック（変更ファイル・テスト結果・残課題）を作ること。push・マージはしない。
